# RCrif Process Viewer

Переделка части с лейаутами из `RCrifLayoutTool` в отдельный инструмент: схема процедуры
рисуется по `Layout.xml`, а поверх неё показывается фактическое прохождение процесса
по конкретной заявке.

## Что сделано по пунктам

| № | Требование | Где реализовано |
|---|---|---|
| 1 | Чтение процесса из указываемой папки, без git | `service/ProcessLoader.kt`. `GitUnit` и вся зависимость от jgit выброшены |
| 2 | Разделённый экран убран | Вместо двух `CodeArea` — одна схема `ui/ProcessDiagramPane.kt` |
| 3 | Прежняя схема обводок убрана | Диффовая раскраска (`diff.css`, `highlightDiff`, `buildSpansAndNav`) удалена целиком. Новая схема подключается реализацией `ui/ActivityOutlineScheme.kt` — есть пустая заготовка `CustomActivityOutlineScheme` |
| 4 | Кружок со счётчиком прохождений | `ProcessDiagramPane.buildCounterNode`, правый верхний угол блока |
| 5 | Зелёная обводка у пройденных | `PassedActivityOutlineScheme` |
| 6 | Прохождение определяется по БД | `db/ActivityPassRepository.kt` |
| 7 | Двойной клик по кружку → дата-документы | `ui/DataDocumentsWindow.kt` |
| 8 | Поле номера заявки рядом с выбором папки | `RCrifProcessViewer.buildTopBar` |
| 9 | Вместо дерева изменений — список процедур | `RCrifProcessViewer.buildProceduresPanel`, данные из `ProcessLoader.procedures()` |

## Трейсы RU Flow

По умолчанию viewer подключается к `jdbc:postgresql://localhost:5432/ru_flow` и читает таблицу
`flow_trace`, которую заполняет RU Flow Engine. Для выбранного номера заявки он показывает:

- число прохождений и фактический маршрут по активностям;
- время начала/завершения каждого вызова и текущую незавершённую активность;
- DataDocument до и после активности;
- `ConnectorInput`, `ConnectorOutput` и текст ошибки для DS-вызовов;
- имя фактического выхода для новых событий движка.

Если выбранный проект дизайнера относится к другой сборке процесса, имена активностей могут
отличаться от runtime-трейса. Viewer сначала сопоставляет их по типу и метаданным активности
(например, `DS_0_00_GetNSValues` из AUTO_CLASSIC 56.220 с
`DS_0_0009_GetNSKeys`, у которого тот же `GetNSValuesConnector`). Неоднозначные совпадения не
угадываются: двойной клик по такой строке открывает исходные DataDocuments, ConnectorInput,
ConnectorOutput и ошибку прямо из `flow_trace`, даже если блока или процедуры нет в layout.
- таблицу всех вызовов заявки по всем процедурам под списком процедур (левая панель разделена
  `SplitPane`); клик по строке открывает процедуру и центрирует схему на активности.

Параметры PostgreSQL меняются через кнопку настроек. Их также можно передать переменными
`RUFLOW_TRACE_DB_URL`, `RUFLOW_TRACE_DB_USER`, `RUFLOW_TRACE_DB_PASSWORD` (либо общими
`DB_URL`, `DB_USER`, `DB_PASSWORD`). Переменные окружения имеют приоритет. Пустой JDBC URL
в настройках переключает приложение обратно на демонстрационную SQLite.

## Вторая итерация

| № | Требование | Где реализовано |
|---|---|---|
| 1 | Блоки и стрелки двигаются удержанием ЛКМ | `ProcessDiagramPane.beginDrag/continueDrag/finishDrag`. Двигается всё выделенное сразу, на отпускании координаты прилипают к сетке `DiagramGeometry.GRID` |
| 2 | Блоки и стрелки кликабельны, чёрная рамка при выборе | `selectActivity` / `selectConnection`, `DiagramStyle.SELECTION_STROKE`. У блока рамка вокруг, у стрелки — чёрная утолщённая линия. Ctrl/Shift — добавить к выделению |
| 3 | Стрелки и размерность блоков как в LayoutMerger | `ui/DiagramGeometry.kt` — фиксированный размер блока и ортогональная трассировка. **Точные значения нужно подтвердить**, см. «Что осталось подключить» |
| 4 | Убраны «Скрыть непройденные» и легенда | Панель схемы теперь содержит только отмену/повтор и масштаб |
| 5 | Отменить / Повторить | `ui/UndoManager.kt`, кнопки на панели, Ctrl+Z, Ctrl+Shift+Z, Ctrl+Y |
| 6 | Мультивыбор рамкой по полю | `installFieldHandlers` — удержание ЛКМ по пустому месту тянет рамку, по отпусканию выделяется всё, что она задела |
| 7 | Цвет для каждого типа блока | `ui/ActivityPalette.kt` |
| 8 | Рендер только видимой части, экономный зум без мыла | `invalidate()` строит узлы только для элементов, пересекающих окно просмотра (+запас `CULL_MARGIN`); ниже масштаба `DETAIL_ZOOM` подписи и счётчики не создаются вовсе. Масштаб — аффинное преобразование `Scale` над векторными фигурами, растровых кэшей нет, поэтому при приближении картинка не мылится |
| 9 | Группировка дата-документов по вызову | `ui/DataDocumentsWindow.kt`: вкладка на каждый вызов, внутри «Данные на старте этого вызова» и «Данные на выходе из этого вызова». Данные отдаёт `ActivityPassRepository.loadActivityCalls` |

Управление схемой: ЛКМ по блоку/стрелке — выбрать, удержание — тащить, Ctrl/Shift+ЛКМ —
добавить к выделению, удержание по пустому полю — рамка мультивыбора, Ctrl+колесо — масштаб.

## Третья итерация

| № | Требование | Где реализовано |
|---|---|---|
| 1 | Асинхронный поиск блока по части названия через регулярку | `service/ActivitySearch.kt` + комбобокс на панели схемы, рядом с кнопками масштаба. Ввод дебаунсится на 250 мс, поиск идёт в отдельном потоке, предыдущая задача отменяется. Запрос разворачивается в регулярку, терпимую к разделителям: `0101Mapping` находит `DM_01_01_MappingA/B/C`. Если запрос сам корректная регулярка — работает и она (`DM_01_.*Mapping[AB]`) |
| 2 | ПКМ по блоку: откуда пришли / куда уйдём | `ProcessDiagramPane.showActivityMenu` — два подменю по входящим и исходящим стрелкам с указанием выхода; выбор пункта переводит выделение на соседний блок и подводит к нему область просмотра |
| 3 | Ctrl+колесо масштабирует в точку под курсором, кнопки — от центра | `RCrifProcessViewer.zoomAt` (якорь) и `zoomAroundViewportCenter` |
| 4 | Мультивыбор дата-документов | `DataDocumentsWindow.table` — `SelectionMode.MULTIPLE`, плюс Ctrl+C / контекстное меню для копирования выделенного в буфер как TSV |

## Четвёртая итерация

Поиск переехал наверх, на панель схемы рядом с кнопками масштаба, и стал редактируемым
комбобоксом: найденное подставляется в выпадающий список, выбор пункта выделяет блок
и подводит к нему область просмотра.

Исправления:

* **Блоки пропадали при масштабировании и при прокрутке.** `pushViewport` считал видимую
  область через `sceneToLocal`, а трансформации после смены масштаба и присвоения
  `hvalue`/`vvalue` пересчитываются только на следующем layout pass — отсечение работало
  по устаревшим координатам. Теперь область считается арифметикой из `hvalue`/`vvalue`,
  размера содержимого и масштаба, тем же способом, что и в `zoomAt`.
* **Клик по пустой области не снимал выделение.** Панель схемы занимает только площадь
  самой схемы, поэтому клик по полю `ScrollPane` за её границей вообще до неё не доходил.
  Обработчик добавлен на `ScrollPane` (клики по скроллбарам отфильтрованы), сама панель
  получила `isPickOnBounds = true`.
* **«Вписать» не подбирала масштаб.** Две причины: нижняя граница `MIN_ZOOM = 0.2`
  не давала уменьшить крупные процедуры, а при вызове сразу после `render` у `ScrollPane`
  ещё нулевой viewport и метод молча выходил. Граница опущена до `0.03`, запрос
  запоминается в `pendingFit` и выполняется, когда придут реальные размеры; добавлен
  отступ `FIT_MARGIN`, чтобы схема не упиралась в края.

## Пятая итерация

**Падение `UnsupportedOperationException` при смене масштаба на крупном лейауте.**
Пересборка сцены меняет `children`, это меняет границы узла, `ScrollPaneSkin` синхронно
правит `hvalue`/`vvalue`, срабатывает слушатель — и `rebuild` вызывался повторно посреди
незавершённого изменения `ObservableList`. `ListChangeBuilder` не реентерабелен, отсюда
исключение. Исправлено тремя вещами:

* `invalidate()` стал защищённой точкой входа: вложенный вызов не выполняется сразу,
  а откладывается флагом `rebuildPending` на следующий пульс;
* панель обрезается по размеру схемы (`contentClip`) — раньше границы узла зависели от того,
  какие узлы сейчас построены, поэтому отсечение само меняло размер содержимого и
  зацикливалось через скроллбар;
* порог «видимая область не изменилась» задан в экранных пикселях, а не в единицах схемы:
  на мелком масштабе одна единица — доли пикселя, и дрожание скроллбара запускало
  пересборку на каждый кадр.

## Ожидаемая структура папки процесса

```
<корень>/
  MainFlow/Layout.xml
  MainFlow/<Активность>/Properties.xml
  Procedures/<Процедура>/Layout.xml
  Procedures/<Процедура>/<Активность>/Properties.xml
```

Процедурой считается `MainFlow` и любая папка внутри `Procedures`, в которой есть `Layout.xml`.
Активности сопоставляются с элементами схемы по `ReferenceName` из `Properties.xml`
(если атрибута нет — по имени папки).

## Что осталось подключить

1. **Геометрия LayoutMerger'а.** В переданных исходниках графического рендера
   LayoutMerger'а нет — вкладка «Marge» показывала `Layout.xml` текстом, поэтому
   «в точности как там» я воспроизвести не мог. Сейчас в `ui/DiagramGeometry.kt` заданы:
   блок 120×60, «хвостик» стрелки от блока 14px, выход/вход строго по центрам сторон,
   сегменты только горизонтальные и вертикальные, шаг сетки 10px. Если исходные правила
   другие — правятся только константы и `route`, отрисовку трогать не нужно.

2. **Схема обводок.** Правила ещё не описаны. Когда будут — реализовать
   `CustomActivityOutlineScheme.applyTo` и присвоить
   `diagram.outlineScheme = CustomActivityOutlineScheme()`; перерисовка произойдёт сама.

3. **История старого CRIF.** Адаптер читает события нового RU Flow. Для подключения
   исторической БД старого ядра понадобится отдельная реализация `ActivityPassRepository`.

## Запуск

```
./gradlew run
```

Выбранная папка и последний номер заявки запоминаются между запусками
(`~/.config/rcrif-process-viewer/config.properties`, на Windows — `%APPDATA%`).
